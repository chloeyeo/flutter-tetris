## Test Framework

**Runner:**
- `flutter_test` (bundled with the Flutter SDK), declared as a `dev_dependency` in `pubspec.yaml:43-44`
- No standalone config file (no `dart_test.yaml`); test discovery relies on Flutter's default `test/` directory convention

**Assertion Library:**
- `matcher`/`flutter_test`'s built-in `expect()` API (transitively included with `flutter_test`) — the only assertion style used in the repo

**Run Commands:**
```bash

flutter test test/widget_test.dart  # Run a specific test file
flutter test --coverage           # Run with coverage (lcov.info output), not currently used in any script
```

## Test Structure

**Current state:** `test/widget_test.dart` still contains the unmodified Flutter starter template's counter-app test:

```dart
void main() {
  testWidgets('Counter increments smoke test', (WidgetTester tester) async {
    await tester.pumpWidget(const MyApp());

    expect(find.text('0'), findsOneWidget);
    expect(find.text('1'), findsNothing);

    await tester.tap(find.byIcon(Icons.add));
    await tester.pump();

    expect(find.text('0'), findsNothing);
    expect(find.text('1'), findsOneWidget);
  });
}
```

**This test is broken/stale relative to the actual app:** `MyApp` (`lib/main.dart:16-27`) renders `GameBoard()`, a Tetris board — there is no counter, no text `'0'`/`'1'` widget, and no `Icons.add` button anywhere in `lib/board.dart`. Running `flutter test` against this file will fail because `find.text('0')` will never resolve. This is the single highest-priority testing gap in the project (see CONCERNS.md if generated).

**Patterns:**
- No setup/teardown helpers exist (no `setUp()`/`tearDown()` calls anywhere)
- No test grouping (`group()`) is used
- No golden-file/screenshot tests
- No pump-and-settle patterns beyond the single `tester.pump()` call in the stale test

## Mocking

**Framework:** None. No `mockito`, `mocktail`, or `fake_async` dependency is declared in `pubspec.yaml`.

**Patterns:** Not applicable — no mocking is performed anywhere in the codebase. Because there is no dependency-injection seam for `AdService`, `SoundService`, or `SharedPreferences`, any future widget test that pumps `GameBoard` directly will attempt real ad loading, real `SharedPreferences.getInstance()` calls, and real audio playback unless these are stubbed at the platform-channel level (e.g. via `SharedPreferences.setMockInitialValues()` or `TestWidgetsFlutterBinding`).

**What to Mock (recommendations for future tests):**
- `SharedPreferences` — use `SharedPreferences.setMockInitialValues({})` before pumping `GameBoard` to avoid `MissingPluginException` in a test environment
- `AdService`/`google_mobile_ads` — the plugin has no test-mode override; ad-related widgets (`BannerAd`, `RewardedAd`) will fail to load in a test harness and must either be disabled via a seam (not currently present) or the ad code path skipped
- `SoundService`/`audioplayers` — already fails silently via try/catch (`lib/sound_service.dart:14-20`), so it is test-safe by accident, but slow/asynchronous in tests

**What NOT to Mock:**
- Pure game-logic classes (`Piece`, `Tetromino`, collision/rotation math in `lib/piece.dart`) have no external dependencies and are ideal candidates for direct unit testing without mocks

## Test Types

**Unit Tests:**
- None exist. High-value untested logic includes: `Piece.rotatePiece()` and its per-tetromino rotation/wall-kick math (`lib/piece.dart:64-271`), `Piece.piecePositionIsValid()` / `positionIsValid()` (`lib/piece.dart:274-309`), `_GameBoardState.checkCollision()`, `clearLines()`, `isGameOver()`, `getGhostPosition()` (`lib/board.dart:277-485`). These are pure/near-pure functions well-suited to unit testing without a widget harness.

**Widget Tests:**
- Only the stale default template exists (`test/widget_test.dart`), and it does not correspond to any real screen in the app. No widget test exercises `GameBoard`, `SkinGallery`, `PiecePreview`, or `Pixel`.

**Integration Tests:**
- Not used. No `integration_test/` package dependency, no end-to-end test harness (e.g. `patrol`).

## Common Patterns

**Async Testing:**
Not demonstrated anywhere in the current test suite. If added, async widget interactions (e.g. `_loadSettings()` awaiting `SharedPreferences.getInstance()` in `lib/board.dart:90-100`) would require `tester.pumpAndSettle()` or explicit `await tester.pump()` cycles to flush pending futures.

**Error Testing:**
Not demonstrated anywhere in the current test suite. No test exercises the `throw UnsupportedError` branches in `lib/ad_service.dart:23,31` or the caught-exception path in `lib/sound_service.dart:14-20`.
